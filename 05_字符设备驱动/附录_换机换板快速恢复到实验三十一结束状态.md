## 一、先分清换的是什么——第 7 章的"家当账本"

一句话总纲：**第 7 章的家当很薄——三件 .ko 和测试程序都住在根文件系统里（跟着 `rfs-buildroot` 走），驱动源码在共享目录（跟着打包走），设备文件在 tmpfs（断电即丢、十秒重建）**。

| 家当 | 住在哪 | 断电/换机后 | 丢了怎么找回来 |
|---|---|---|---|
| 驱动源码 + 编译产物 | **共享目录** `<共享目录>/drivers-dev/01-toychar/`（toychar1/2/3.c、Makefile、三件 .ko、toycharApp） | 换电脑就丢 | 本册步骤 1（解压素材 + `make`，几分钟） |
| 三件驱动模块 | **根文件系统里** `rfs-buildroot/lib/modules/5.4.31/*.ko`（Ubuntu 的 NFS 导出目录） | 跟 `rfs-buildroot` 的命运走：整包带走则在；只带 rootfs.tar 重解包则丢 | 本册步骤 2（sudo cp 三件 + 板上 depmod，两分钟） |
| modules.dep 登记 | 同上目录的 `modules.dep`（板上 depmod 的产物，**落在 Ubuntu 侧的根里**） | 同上——**登记随根持久保存，只换板子不用重做** | 板上重跑一次 `depmod`（十秒） |
| 测试程序 toycharApp | `rfs-buildroot/bin/toycharApp`（12,312 字节） | 同 .ko | 本册步骤 3（交叉编译 + sudo cp） |
| 设备文件 /dev/toychar | **板上 tmpfs**（/dev） | **断电/复位即丢——属设计，不是丢家当** | 用前 `mknod /dev/toychar c 200 1`（十秒，本册步骤 4） |
| 内核里的模块加载状态 | 板上内存 | 断电即清 | `modprobe` 重载（登记在，秒级） |

| 场景 | 必做步骤 | 可以跳过 |
|---|---|---|
| 只换开发板（电脑与卡不动） | 第三册步骤 3（板侧启动指向）→ 本册步骤 4（验收） | **本册步骤 1~3 全部**——.ko、登记、toycharApp 都在 Ubuntu 的 NFS 根里，板子换了照样在 |
| 换电脑，`rfs-buildroot` 整包带过来了（第三册步骤 2 路线 a） | 第三册步骤 1~4 → 本册步骤 1（源码复编，练手）→ 步骤 4 | 步骤 2/3——.ko 与 toycharApp 在包里，modules.dep 登记也在 |
| 换电脑，**只带了 rootfs.tar**（第三册步骤 2 路线 b） | 第三册步骤 1~4 → 本册步骤 1 → 2 → 3 → 4 | 无 |
| 只是不小心删了 .ko 或登记乱了 | 本册步骤 2 → 步骤 4 | 其余全部 |

**最容易白做的一件事**：以为"模块在板子上"，换板就慌。第 7 章起驱动模块住的是**根文件系统**（Ubuntu 的 NFS 目录），板子只是"挂根使用"——换板、换卡都不动它；真正断电即失的只有 /dev/toychar 设备文件和内核内存里的加载状态，两者都是十秒级重建。

## 二、恢复目标：实验三十一结束态的验收判据

**一句话**：第三册的四条判据（无人值守点火进 buildroot 根）全过之外，toychar 全链随时可以复跑。

逐项判据（三条全过 = 实验三十一结束态）：

1. **模块在册**：板上 `cat /lib/modules/5.4.31/modules.dep | grep toychar` 见三行 `toychar1.ko:`/`toychar2.ko:`/`toychar3.ko:`（Ubuntu 侧看 `/home/cnu/nfsboot/rfs-buildroot/lib/modules/5.4.31/` 同样三件，且 `ls /home/cnu/nfsboot/rfs-buildroot/bin/toycharApp` 在）；
2. **toychar1 加载/卸载**：`modprobe toychar1` 后 dmesg 见 `toychar init!`（**taint 提示属正常**，按方案 1 无视），`rmmod toychar1` 后 `toychar exit!`；
3. **toychar3 全链**：`modprobe toychar3` → `mknod /dev/toychar c 200 1` → `toycharApp /dev/toychar 1` 读回 `read data:kernel data!`（内核侧 `kernel senddata ok!` 同屏）→ `toycharApp /dev/toychar 2` 后 dmesg 见 `kernel recevdata:usr data!`。

## 三、步骤 1：驱动素材与编译（换电脑才做）

素材包 `drivers-dev.zip`（md5 `7fa1d58d1e6f082f4f553230bde7ddcb`）在仓库 `05_字符设备驱动/` 目录，拷进共享目录解压：

```bash
# 【Ubuntu 侧执行】
cd <共享目录>
unzip drivers-dev.zip
cd drivers-dev/01-toychar
ls    # Makefile  toychar1.c  toychar2.c  toychar3.c  toycharApp.c
```

**第 1 行 KERNELDIR 必改**——zip 里预填的是课件作者机器的路径（`/home/cnu/share/FS-MP1A/...`），照抄必报 `没有那个文件或目录`（实验三十一第一个实测坑）。改成你的内核树、**先 ls 验路径再 make**：

```bash
# 【Ubuntu 侧执行，01-toychar/ 里】
nano Makefile     # Ctrl+W 搜 KERNELDIR，第 1 行改成你的内核树路径，尾随 / 保留
ls <你的内核树>/Makefile    # 先验路径存在，回显原路径 = 对了
make
ls *.ko                              # toychar1.ko toychar2.ko toychar3.ko
modinfo toychar1.ko | grep vermagic  # 5.4.31 开头 = 与板上内核同源
```

**编译不用 source /stm32env**——内核树顶层 Makefile 自带 ARCH/CROSS_COMPILE，工具链用 PATH 里的 `arm-none-linux-gnueabihf-`（第二册步骤 1 装的 gcc-arm-9.2）。

## 四、步骤 2：模块部署 + 登记（.ko 或登记缺才做）

```bash
# 【Ubuntu 侧执行，01-toychar/ 里】
sudo cp toychar1.ko toychar2.ko toychar3.ko /home/cnu/nfsboot/rfs-buildroot/lib/modules/5.4.31/
ls /home/cnu/nfsboot/rfs-buildroot/lib/modules/5.4.31/*.ko    # 三件就位
```

```bash
# 【板上执行，root/123 登录】
depmod                                        # 登记进 modules.dep
cat /lib/modules/5.4.31/modules.dep | grep toychar    # 三行 = modprobe 找得到了
```

**凡往 rfs-buildroot 拷文件一律 sudo**——实验二十九 chown 归位后普通用户写入必报"权限不够"（实验三十一实测三连报），不是根坏了。

## 五、步骤 3：测试程序（bin 里缺才做）

```bash
# 【Ubuntu 侧执行，01-toychar/ 里】
arm-none-linux-gnueabihf-gcc toycharApp.c -o toycharApp
file toycharApp    # ELF 32-bit ... ARM, EABI5 = 对了再拷
sudo cp toycharApp /home/cnu/nfsboot/rfs-buildroot/bin/
```

## 六、步骤 4：验收——toychar 全链复跑

```text
【板上】
modprobe toychar3                          # toychar init!（taint 提示无视）
mknod /dev/toychar c 200 1                 # /dev/toychar 断电即丢，用前重建
ls -l /dev/toychar                         # crw-r--r-- ... 200, 1 = 对了
toycharApp /dev/toychar 1                  # read data:kernel data!（内核 senddata ok! 同屏）
toycharApp /dev/toychar 2                  # dmesg 见 kernel recevdata:usr data!
rmmod toychar3 && rm /dev/toychar          # 收尾
```

三条判据全过 = **恢复到实验三十一结束状态**，第 8 章可直接开跑。

## 七、避坑清单（第 7 章专属，条条实测踩过）

1. **凡往 rfs-buildroot 拷文件一律 sudo**——实验二十九 chown 归 root 的直接后果；普通 cp 报"权限不够"不是坏了。
2. **taint 提示不是报错**——`module verification failed ... tainting kernel` 照打不误、模块照常加载（内核没开 `MODULE_SIG_FORCE`）；`lsmod` 表头 `Tainted: G` 是同一件事的登记（G = GPL 模块触发的弄脏标记）。
3. **toychar2 与 toychar3 同占主设备号 200**——同时加载必有一个 `toychar driver register failed`；验完一个先 `rmmod` 再加载下一个。
4. **/dev/toychar 在 tmpfs 上，断电/复位即丢**——属设计；设备文件丢了 `mknod` 十秒重建，别当成"驱动坏了"。
5. **模块与内核必须同源**——编译器（gcc-arm-9.2）与编内核同一套、`/lib/modules/5.4.31/` 目录名与 `uname -r` 一致；对不上加载报 `Invalid module format`，第一反应查 vermagic。
6. **改了源码重编后，板上先 `rmmod` 再 `modprobe`**——NFS 根里 .ko 是新的，内核内存里还是旧的。

## 八、恢复完成标志

- `<共享目录>/drivers-dev/01-toychar/` 五件套在，`make` 可复编（换电脑自检）
- `rfs-buildroot/lib/modules/5.4.31/` 三件 .ko 在、modules.dep 三行登记在
- `rfs-buildroot/bin/toycharApp` 在（12,312 字节）
- 板上三条判据全过（本册第二节）
