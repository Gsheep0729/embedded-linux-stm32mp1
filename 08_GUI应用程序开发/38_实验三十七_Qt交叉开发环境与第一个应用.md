# 实验三十七 Qt 交叉开发环境与第一个应用——屏幕上的 Hello world

> **对应课件**：《第10章 GUI应用程序开发》10.4~10.5 节，Slide 27-55
>
> **系列说明**：本系列基于华清远见 FS-MP1A（STM32MP157A）开发板，对应课件《第10章 GUI应用程序开发》。全系列收官篇：实验三十六把 QT 运行环境与部署通道（ssh/gdbserver）建好，本篇在电脑上配 Qt Creator——把 buildroot 生成的交叉工具链登记成 Kit、把开发板登记成设备——然后导入 Hello world 项目，**编译 → 一键部署 → LCD 屏亮出按钮 → 远程断点调试**一气呵成。做完这篇，"在 Ubuntu 写代码、在板子的屏幕上见效"的完整开发闭环就通了。前置：实验三十六（QT 运行环境 + ssh 通）。

## 一、交叉开发的角色分工

| 角色 | 在哪 | 干什么 |
|---|---|---|
| Qt Creator + Kits | Ubuntu（Host） | 写代码、调交叉编译器编出 ARM 程序、经 ssh 部署、远程 gdb 调试 |
| buildroot 产物 output/host/ | Ubuntu | Kit 的全部弹药：`arm-none-linux-gnueabihf-gcc/g++/gdb`、`qmake`（Qt 5.12.8）、sysroot |
| 开发板（Target） | 板上 | 跑 gdbserver 收部署的程序、LCD 显示（出厂内核 + linuxfb） |

## 二、实验环境（实际）

| 项目 | 实际值 |
|---|---|
| Host | Ubuntu 虚拟机：`sudo apt install qtcreator`（桌面版 VM 需有图形界面） |
| 弹药库 | `<buildroot源码>/output/host/bin/`（实验三十六编译产出） |
| Target | 板子：`run fcsys` 出厂内核 + 新根（QT 运行环境/ssh/gdbserver 就位），IP `.8` |
| 项目 | `main.cpp` + `qt-demo-qc.pro`（课件 Slide 44 给了 main.cpp 全文；.pro 按标准模板自建，见步骤 4） |

> **开工自检（10 秒）**：`ls <buildroot源码>/output/host/bin/qmake` 在；板上 ssh root@192.168.0.8 能登（实验三十六步骤 7）；屏上 calculator 上一课还点得动。

### 步骤 4：导入项目（Slide 44~48）

项目就两个文件。`main.cpp`（课件 Slide 44 全文）：

```cpp
#include <QApplication>
#include <QPushButton>

int main(int argc, char* argv[])
{
    QApplication app(argc, argv);
    QPushButton hello("Hello world!");
    hello.resize(100,30);
    hello.show();
    return app.exec();
}
```

`qt-demo-qc.pro`（qmake 工程文件，按标准模板）：

```pro
QT += widgets
SOURCES += main.cpp
TARGET = qt-demo

target.path = /opt
INSTALLS += target
```

（课件提示"内容如下"后给了 main.cpp；.pro 的 `QT += widgets` 对应实验三十六勾的 Widgets 库、`TARGET` 是产物名。**后两行是部署规则，实测缺它不可**：Build 后 Qt Creator 经 SFTP 把产物传到板上 `/opt/qt-demo`——没有这两行，Run 会报 `Cannot run: No command given.`（Qt Creator 不知道把程序放哪、跑哪个）。**target.path 写 `/opt` 别写成 `/opt/$${TARGET}`**——后者会让部署先在板上建 `/opt/qt-demo` 子目录，而这块板的 SFTP 服务建目录报 Failure（实测，见步骤 5 踩坑）。）

**先回答"导入的是什么项目"**：不是 Qt Quick 模板——Qt Quick 是 QML 技术栈，本篇用的是 **Qt Widgets**（`QT += widgets` + QPushButton）。做法二选一：

- **方法 A（课件路线，推荐）**：新建一个空目录（如 `qt-demo-qc`），手建上面两个文件（main.cpp 照课件全文抄），然后 File → Open File or Project 选 `qt-demo-qc.pro`——文件最少、与课件逐字对应；
- **方法 B（模板起头）**：File → New File or Project → Application (Qt) → **Qt Widgets Application**（注意**不是 Qt Quick Application**），Build system 选 qmake——模板会多生成 mainwindow 一套文件（用不上可删），再把 main.cpp 改成课件全文。

两条路最终的项目内容完全一样；下面的 Open → Configure Project 流程两条路都适用。

**实测踩坑：Open 之后两个 kit 全灰、提示 "No suitable kits found."**——项目文件先 `cat` 核对过没问题，桌面 kit 灰也正常（没装宿主 Qt）。两层原因、两条修法，**先抄修法，原理与排查链在后面**：

```text
第一层  output/host/mkspecs/ 里缺 default 符号连接 → 整个 Qt 版本被判无效 → kit 全灰
修法    ln -sfn devices/linux-buildroot-g++ <buildroot源码>/output/host/mkspecs/default

第二层  kit 的 Qt version 字段掉成 None → default 补上后仍灰
修法    Kits 页选中 kit → Qt version 下拉选回 Qt 5.12.8 (Buildroot)；删掉自动生成的 "- temporary" 临时 kit
```

排查链（含两次被否的假设，照抄链路就能自救）：

① 用 qmake 问出 mkspec 的查找基准——**`QT_HOST_DATA` 才是 mkspecs 的家**（别查 sysroot，那是头一个会踩的弯路）：

```bash
~/Desktop/LINUX-gy/Test2/buildroot-2020.02.6/output/host/bin/qmake -query | grep -E "QT_HOST_DATA|QMAKE_XSPEC"
# QT_HOST_DATA: .../output/host                     ← mkspecs 在它下面的 mkspecs/ 里
# QMAKE_XSPEC: devices/linux-buildroot-g++          ← qmake 配置里烙的目标 spec
```

② 排除"spec 缺失"假设——devices 目录实测在位（linux-buildroot-g++ 在列），假设否掉：

```bash
ls ~/Desktop/LINUX-gy/Test2/buildroot-2020.02.6/output/host/mkspecs/devices/
```

③ 真凶之一：**mkspecs/default 符号连接缺失**（`ls -la .../mkspecs/ | grep default` 空输出）。修法一行——**注意路径要写全，别把省略号当路径照抄**：

```bash
ln -sfn devices/linux-buildroot-g++ ~/Desktop/LINUX-gy/Test2/buildroot-2020.02.6/output/host/mkspecs/default
ls -la ~/Desktop/LINUX-gy/Test2/buildroot-2020.02.6/output/host/mkspecs/ | grep default
# default -> devices/linux-buildroot-g++  = 第一层补上了
```

**但实测补上、连 Ubuntu 都重启了，kit 仍灰**——default 缺失是"必要不充分"的第一层，底下还有第二层。继续定位的手段（按顺序，谁先出红字谁就是答案）：

- Configure Project 页 Buildroot ARM 行的"**详情**"下拉展开——红字直接写 kit 哪里不合格；
- Kits 页选中 Buildroot ARM——下方 Name/Device type/编译器/调试器/Qt version 各字段**哪个带 ⚠ 图标**；
- Qt Versions 页选中 Qt 5.12.8 (Buildroot)——**详情顶部的黄色警告条**全文（常见嫌疑："Qt version is not properly installed"）；
- 终端兜底验证四件套真能跑：

```bash
B=~/Desktop/LINUX-gy/Test2/buildroot-2020.02.6/output/host/bin
ls $B | grep -E "gcc$|g\+\+$|gdb$|qmake$"
$B/arm-none-linux-gnueabihf-g++ --version | head -1
$B/qmake --version
```

**实测进展（工具链洗清嫌疑）**：命令行 `qmake qt-demo-qc.pro && make` 直接编出 ARM 产物（file 见 EABI5）、四件套全部能跑、qmake 报 Qt 5.12.8 指向 sysroot/usr/lib——**工具链与 Qt 完全健康，问题收敛在 Qt Creator 的 kit 判定**。下一号嫌疑：**Qt 的模块描述文件 qt_lib_*.pri 的位置**——`QT += widgets` 的项目要求 kit 的 Qt 提供 widgets 模块，Qt Creator 按 `QT_INSTALL_ARCHDATA/mkspecs/modules`（sysroot/usr/mkspecs/modules）找它们，实测该目录不存在（模块 .pri 实际生成在 output/host/mkspecs/modules/）。修法：把编译目录的 mkspecs 补进 sysroot：

```bash
cp -a ~/Desktop/LINUX-gy/Test2/buildroot-2020.02.6/output/build/qt5base-5.12.8/mkspecs \
      ~/Desktop/LINUX-gy/Test2/buildroot-2020.02.6/output/host/arm-buildroot-linux-gnueabihf/sysroot/usr/
```

补完重启 Qt Creator 重新 Open 项目——Buildroot ARM 若能打勾，根因坐实；仍灰则看"详情"红字。

**第二层答案（实测截图对照出的）**：default 连接补上、整机重启后 kit 仍灰——重新 Open 项目时 Qt Creator **自动生成了一个 `Qt 5.12.8 (Buildroot) - temporary` 临时 kit**（Kits 列表里带 ⚠ 的那个），同时手动 kit 的 **Qt version 字段掉成了 `None`**。两步修复：

```text
1. Kits 页选中 Buildroot ARM → Qt version 下拉重新选回 Qt 5.12.8 (Buildroot)
2. 选中多余的临时 kit "Qt 5.12.8 (Buildroot) - temporary" → 删除
```

Apply/OK 后重新 Open 项目——Buildroot ARM 从灰变可选、勾上后 Configure Project 可点（桌面 kit 依旧灰——没装宿主 Qt，本篇用不上也不用管）。

**转正收尾两个动作**：① 转正 kit 的**名称改成 `Buildroot ARM`**、删掉旧灰 kit——与本篇正文名字一致；② 转正 kit 的字段此时已四项齐全（Device/Sysroot/编译器/调试器/Qt 版本/mkspec 一应俱全——临时 kit 转正时这些会一并带过来或补选）。

**两个追问的答案**：① 临时 kit 哪来的——Qt Creator 的标准自救：打开项目时发现项目的 Qt 版本没有可用 kit，它会**用该 Qt 版本自动现配一个临时 kit**（名字 = Qt 版本名 + " - temporary"）让项目至少能配；② 原 Buildroot ARM 为什么灰——它的 **Qt version 字段是 None**（配置页截图实锤）。None 怎么来的：default 符号连接缺失期这个 Qt 版本被判无效，kit 字段在那阵被重置/未选上的概率最大（确切时机已不可考，也不重要）——**Qt Creator 修好 Qt 版本后不会自动把 kit 的字段补回来，要手动选回**；你选择了更省事的转正路线，效果相同。

**实测踩坑：运行参数没加，报 `Could not find the Qt platform plugin "eglfs"`、程序起崩**（按"现象 → 根因 → 修法"记）：

- **现象**：点绿色三角，`Starting /opt/qt-demo ...` 之后红字连发：`qt.qpa.plugin: Could not find the Qt platform plugin "eglfs" in ""` → `This application failed to start because no Qt platform plugin could be initialized.` → `Remote process crashed.`。中间夹着一行**关键证据**：`Available platform plugins are: linuxfb, minimal, offscreen, vnc`——**板上不缺后端，linuxfb 明明在列**（实验三十六的 calculator、本篇的手动路线都已在 linuxfb 上跑通过）。
- **根因**：Qt 选显示后端的优先级 = `-platform` 命令行参数 > `QT_QPA_PLATFORM` 环境变量 > **编译期写死的默认值（这套 Qt 默认 eglfs）**。前两级都没传到，Qt 就奔默认的 eglfs 去——而 buildroot 这套只编了 linuxfb 后端（实验三十六实测：不开 OpenGL 连 eglfs 选项都不出现），插件不存在 → 启动即崩。**程序没问题、板子没问题，就是参数没挂上**。
- **修法**：上图的 Command line arguments 填 `-platform linuxfb`，点绿色三角重新运行即过（实测）。认准这个框——它下面的 **Alternate executable on device** 是"整条命令替换"的备用框，参数别填那里。

**实测踩坑：点绿色三角报 `File transfer failed: Couldn't create directory: Failure` ×3 + `remote open("/opt/qt-demo/qt-demo"): No such file or directory`**——部署规则写成 `target.path = /opt/$${TARGET}` 时，Qt Creator 会先经 SFTP 在板上**创建 /opt/qt-demo 子目录**再传文件，而这块板的 SFTP 服务对建目录直接报 Failure（目录建不成，文件自然落不下）。修法（二选一）：

- **改 .pro（推荐，与课件一致）**：`target.path = /opt`——产物直接落 `/opt/qt-demo`、不建子目录，重新 Build 再 Run；
- **预建目录**：Ubuntu 侧 `sudo mkdir -p /home/cnu/nfsboot/rfs-buildroot/opt/qt-demo`（NFS 两副面孔），SFTP 只需传文件。

点左下角**绿色三角**（运行按钮）——编译产物经 SFTP 部署到板上（.pro 里可指定目标目录，课件示例部署到 /opt）并运行：

### 步骤 6：断点调试（Slide 53~55）

调试前两件事：**① Projects → Build 里取消 Shadow build**（产物要留在项目目录里，gdb 才找得到源码与符号）；**② .pro 加编译参数**（-g 带调试信息——缺了进不了断点；-O0 不优化——缺了单步会跳行、变量被优化掉看不到）。改完后的 .pro 全文如下（末行是新加的，其余与步骤 4 一致，可整块复制覆盖）：

```pro
QT += widgets
SOURCES += main.cpp
TARGET = qt-demo

target.path = /opt
INSTALLS += target

QMAKE_CXXFLAGS += -g -O0
```

![取消Shadowbuild](./38_实验三十七_Qt交叉开发环境与第一个应用.assets/32_取消Shadowbuild.png)
> 图：课件 Slide 53——Build Settings 页：Shadow build 复选框取消勾选；Build Steps 显示 qmake -spec devices/linux-buildroot-g++ 与 make。

main.cpp 整份换成下面这份（可整块复制覆盖；新内容 = `int a = 42;`/`a++` 给断点处的局部变量窗口看值，`qDebug("Test 1")`/`qDebug("Test 2")` 在应用程序输出窗各打一行——printf 风格的 qDebug 走 QtGlobal 自带声明，不用另加 `#include <QDebug>`，带 `<<` 的流式写法才需要）：

```cpp
#include <QApplication>
#include <QPushButton>

int main(int argc, char* argv[])
{

    a++;

    QApplication app(argc, argv);
    QPushButton hello("Hello world!");
    hello.resize(100,30);
    hello.show();
    qDebug("Test 2");
    return app.exec();
}
```

## 五、注意事项

1. **Kit 四项弹药全部指向 buildroot 的 output/host/**——别混用实验十九的裸编译器（qmake 与 sysroot 必须配套，混搭编出的程序在板上缺库）。
2. **mkspec 手填 `devices/linux-buildroot-g++`**——下拉列表里没有，手敲；填错 qmake 会用宿主规格编出 x86 程序。
3. **设备 IP 填我们板的 `.8`**；Test 报 rsync not found 是正常降级（SFTP 部署），不算失败。
4. **红色波浪线先怀疑 ClangCodeModel**——关插件重启，别按"报错"去改代码（代码本身没毛病）。
5. **`-platform linuxfb` 是运行参数不是编译参数**——Run 设置的 Command line arguments 里加（实测漏加必报 eglfs 起崩，见步骤 5 踩坑）；命令行手动跑时同样要带。
6. 调试不起断点：Shadow build 取消没、-g -O0 加了没、部署的是重编后的版本（改代码要重新 Build）。
7. 板子要一直在位（ssh/gdbserver 都走网络）；板重启后 gdbserver 由 init 脚本自动起，Qt Creator 重新点运行即可。
